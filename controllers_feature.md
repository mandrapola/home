# Перспективные конфигурации контроллеров

## Zigbee-станция беспроводных датчиков

### Статус
Планируемый тип контроллера. В текущем дереве `client/controller/` отдельного скетча для Zigbee-станции нет.

### Назначение
Zigbee-станция принимает данные от беспроводных Zigbee-датчиков, распознает известные устройства, агрегирует последние показания и отправляет их на сервер одним report-запросом.

Цель станции — уменьшить количество прямых запросов от отдельных датчиков к серверу и убрать необходимость тянуть провода к удаленным точкам измерения.

### Роль в архитектуре
- Zigbee-датчики работают как беспроводные измерительные узлы.
- Станция выполняет роль координатора/шлюза Zigbee-сети.
- Сервер видит станцию как обычный контроллер пользователя.
- Каждый Zigbee-датчик или его канал отображается на сервере как отдельный sensor-пин станции.
- Сценарии могут использовать показания Zigbee-датчиков для управления реле других контроллеров пользователя.

### Идентификация Zigbee-датчиков
- Основной стабильный идентификатор устройства — `IEEE address` / `EUI64`.
- `network address` / short address не использовать как постоянный ID, так как он может меняться внутри Zigbee-сети.
- Для диагностики и автодетекта сохранять `manufacturer`, `model_id`, `endpoint` и список `clusters`.
- Рекомендуемый `device_uid` для датчика: `zigbee_<ieee_address>`, например `zigbee_00158d0007abcd12`.

### Определение типа датчика
Тип датчика определяется по Zigbee clusters и, при необходимости, по `manufacturer + model_id + endpoint`.

Стандартные примеры:
- `0x0402 Temperature Measurement` -> температура
- `0x0405 Relative Humidity Measurement` -> влажность воздуха
- `0x0400 Illuminance Measurement` -> освещенность
- `0x0001 Power Configuration` -> батарея
- `0x0500 IAS Zone` -> охранные датчики; конкретный тип уточняется по zone type

Для Tuya/Aqara и части совместимых датчиков может потребоваться отдельный маппинг модели, так как они часто используют manufacturer-specific clusters/datapoints.

### Требования к станции
- Поддержка Zigbee coordinator mode.
- Прием данных от всех распознанных Zigbee-датчиков в зоне связи.
- Автоматическое добавление известных датчиков/каналов в report payload.
- Отправка агрегированного JSON report-contract на сервер.
- Использование обычного pairing/provisioning flow AiDvor.
- Использование bearer token после регистрации.
- Локальная страница настроек по аналогии с ESP8266:
  - `/local`
  - `/status`
  - `/config`
  - fallback AP при ошибке Wi-Fi
  - Basic Auth
  - `config.txt`
  - `ca.pem`

### Требования к Zigbee-датчикам
- Датчики не должны напрямую отправлять данные на сервер.
- Датчики передают данные только станции.
- Станция принимает сигналы от всех датчиков, которые может распознать.
- Список датчиков не должен быть жестко зашит в прошивку станции.
- Неизвестные датчики можно игнорировать или отображать как неподдерживаемые до добавления маппинга.

### Формирование telemetry keys
Рекомендуемый формат `readings[].pin`:

- `zigbee_<ieee_address>_soil_moisture_raw`
- `zigbee_<ieee_address>_soil_temperature`
- `zigbee_<ieee_address>_air_temperature`
- `zigbee_<ieee_address>_air_humidity`
- `zigbee_<ieee_address>_light_level_raw`
- `zigbee_<ieee_address>_battery`
- `zigbee_<ieee_address>_link_quality`

Для пользовательского интерфейса человекочитаемые названия должны задаваться на сервере в настройках пина.

### Калибровка
- Калибровка датчиков хранится на сервере.
- Станция отправляет сырые или штатные значения датчика без локального пересчета в пользовательские проценты.
- Для влажности почвы предпочтительно хранить `dry/wet` калибровку в настройках server-side pin.

### Отказоустойчивость
- Если отдельный Zigbee-датчик временно недоступен, станция не должна блокировать отправку данных остальных датчиков.
- Для каждого датчика желательно хранить `last_seen_at` на сервере.
- Старые значения не должны маскироваться как новые: сервер должен понимать время последнего обновления пина.
- Если станция потеряла связь с сервером, локальная страница должна показывать последние принятые значения.

### Ограничения MVP
- Без локальной истории на станции.
- Только последние значения датчиков.
- Без локальной автоматизации на станции.
- Управление сценариями остается на сервере.
- Поддержка только заранее описанных типов Zigbee-датчиков.

## Контроллер котельной

### Статус
Планируемый тип контроллера. В текущем дереве `client/controller/` отдельного скетча для котельной нет.

### Возможная аппаратная база
Рассматриваются два варианта на существующих комплектующих:

- `Arduino Uno R3 + Ethernet Shield`
- `Arduino Uno R4 WiFi`

Для нового прототипа предпочтительнее `Arduino Uno R4 WiFi`, если требуется меньше внешних модулей и проще сетевое подключение. Вариант `Arduino Uno R3 + Ethernet Shield` можно использовать, если важнее проводная сеть и уже есть стабильная Ethernet-инфраструктура.

### Назначение
Контроллер котельной предназначен для мониторинга состояния отопления и водоснабжения, раннего обнаружения аварийных режимов и передачи телеметрии на сервер AiDvor.

MVP должен быть ориентирован на мониторинг. Прямое управление насосами или котлом требует отдельного проектирования защиты и не должно добавляться без аппаратных предохранителей, ручного режима и fail-safe логики.

### Контролируемые параметры
- Температура теплоносителя на подаче.
- Температура теплоносителя на обратке.
- Температура теплоносителя на выходе из котла.
- Давление в системе отопления.
- Состояние работы насосов.
- Давление в гидроаккумуляторе.
- Давление в системе водоснабжения.

### Рекомендуемые датчики
- Температура теплоносителя: герметичные `DS18B20` в гильзах или накладные датчики на трубу с теплоизоляцией.
- Давление отопления: аналоговый датчик давления с диапазоном, подходящим системе отопления, например `0-5 bar` или `0-10 bar`, выход `0.5-4.5V` либо `0-5V`.
- Давление водоснабжения/гидроаккумулятора: аналоговый датчик давления с диапазоном под насосную станцию, например `0-10 bar`.
- Контроль работы насосов:
  - датчик тока на линии питания насоса;
  - либо сухой контакт/сигнальный выход реле/автоматики, если доступен;
  - либо контроль напряжения через безопасный гальванически развязанный модуль.

### Требования к безопасности
- Не подключать сетевое напряжение 220V напрямую к Arduino.
- Все сигналы от насосов и автоматики 220V должны поступать через гальваническую развязку.
- Силовое управление котлом и насосами не включать в MVP без отдельного аппаратного проекта.
- Для датчиков давления проверить совместимость выходного напряжения с входами контроллера.
- Для Arduino Uno R3 аналоговые входы допускают до 5V; для других плат проверять допустимые уровни отдельно.
- Датчики на трубах должны быть механически закреплены и защищены от влаги/конденсата.

### Рекомендуемые telemetry keys
- `heating_supply_temperature` -> температура теплоносителя на подаче
- `heating_return_temperature` -> температура теплоносителя на обратке
- `boiler_output_temperature` -> температура теплоносителя на выходе из котла
- `heating_pressure` -> давление в системе отопления
- `pump_1_running` -> состояние насоса 1
- `pump_2_running` -> состояние насоса 2, если установлен
- `hydroaccumulator_pressure` -> давление в гидроаккумуляторе
- `water_supply_pressure` -> давление в системе водоснабжения

### Рекомендации по сценариям
Сценарии сервера могут использовать показания котельной для уведомлений и аварийных признаков:

- слишком высокая температура на выходе из котла;
- слишком низкая температура подачи при включенном отоплении;
- большая разница между подачей и обраткой;
- падение давления в отоплении ниже допустимого порога;
- рост давления выше допустимого порога;
- насос не работает при ожидаемой циркуляции;
- частое падение давления в гидроаккумуляторе;
- отсутствие обновления данных от контроллера.

### Ограничения MVP
- Только мониторинг и отправка телеметрии.
- Без локальной истории на контроллере.
- Без прямого управления котлом.
- Без прямого силового управления насосами.
- Калибровка датчиков давления хранится на сервере в настройках пинов.
- Человекочитаемые названия пинов задаются на сервере.
